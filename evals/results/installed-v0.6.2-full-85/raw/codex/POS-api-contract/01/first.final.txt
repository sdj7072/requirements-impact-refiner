## Change Impact Summary

### Impact IMP-001

- Changed feature: The API field becomes profile.name.
- Possible issue: Existing iOS builds can no longer decode the user's display name if the old field disappears immediately.
- Affected feature or user: Released iOS clients and any staged rollout in which server and app versions differ.
- Trigger: A response contains only profile.name while the client still requests profile.displayName.
- Severity: high
- Prevention or check: Choose either a one-release alias/fallback rollout or a coordinated breaking update of producer and client.
- Status: detected

### Impact IMP-002

- Changed feature: The canonical persisted profile key becomes profile.name.
- Possible issue: Existing cached records may be unreadable or may continue reintroducing the deprecated key.
- Affected feature or user: Users with cache entries written before the rename and code paths reading cached profiles.
- Trigger: New code reads only profile.name from an entry stored with profile.displayName, or keeps writing the legacy key.
- Severity: high
- Prevention or check: Define read-old/write-new migration behavior for one release, or invalidate/migrate all cache entries during a coordinated breaking rollout.
- Status: detected

### Impact IMP-003

- Changed feature: profile.displayName becomes deprecated in favor of profile.name.
- Possible issue: The implementation may either remove the old field too early or leave the changelog/policy record inconsistent with the actual rollout.
- Affected feature or user: Release coordination, maintainers, and downstream consumers relying on the stated compatibility window.
- Trigger: The API rename ships without updating the deprecation record and removal timing.
- Severity: medium
- Prevention or check: Record the replacement and apply the configured one-release compatibility window, unless an explicit breaking rollout is selected.
- Status: detected

## Decision Needed

- Question: Should the rename honor the configured one-release deprecation window, or be an immediate coordinated breaking change?

### Option 1

- Option: One-release compatibility rollout
- Affected impacts: IMP-001, IMP-002, IMP-003
- Trade-off: Temporarily support profile.displayName alongside profile.name; update iOS to prefer the new key with old-key fallback, migrate cache reads/writes, then remove the alias after one release.

### Option 2

- Option: Immediate coordinated rename
- Affected impacts: IMP-001, IMP-002, IMP-003
- Trade-off: Update API, iOS decoder, cache format/migration, and changelog together now; simpler end state, but incompatible with already-released clients and old cached data unless deployments and invalidation are tightly coordinated.
