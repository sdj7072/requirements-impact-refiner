## Change Impact Summary

### Impact IMP-001

- Changed feature: Profile API field name
- Possible issue: The iOS client may fail to populate the user's display name.
- Affected feature or user: iOS profile decoding and dependent user-facing views.
- Trigger: The API begins publishing profile.name while UserDTO still requests profile.displayName.
- Severity: high
- Prevention or check: Choose either a one-release compatibility alias or a coordinated breaking update of the iOS decoder.
- Status: blocked

### Impact IMP-002

- Changed feature: Persisted profile field key
- Possible issue: Existing cached names may become unreadable or coexist with a second key, causing stale or missing values.
- Affected feature or user: Profile cache reads, writes, and existing persisted entries.
- Trigger: New API responses use profile.name while cache code and stored data remain keyed by profile.displayName.
- Severity: high
- Prevention or check: Define dual-read or migration behavior for the compatibility window, or coordinate an explicit cache migration with the rename.
- Status: blocked

### Impact IMP-003

- Changed feature: Profile field deprecation lifecycle
- Possible issue: Immediate removal may violate the repository's one-release deprecation policy, while documentation may advertise the wrong active or deprecated key.
- Affected feature or user: API compatibility guarantees, release notes, and downstream migration timing.
- Trigger: profile.displayName is removed without defining the configured one-release transition.
- Severity: medium
- Prevention or check: Select and document either a one-release alias period or an intentional breaking-release override.
- Status: blocked

## Decision Needed

- Question: How should the known consumers and the configured one-release deprecation window be handled?

### Option 1

- Option: One-release compatibility migration
- Affected impacts: IMP-001, IMP-002, IMP-003
- Trade-off: Publish profile.name while retaining profile.displayName for one release, update iOS and cache behavior during that window, then remove the alias; this preserves compatibility but requires transitional code.

### Option 2

- Option: Coordinated immediate breaking rename
- Affected impacts: IMP-001, IMP-002, IMP-003
- Trade-off: Rename the API, iOS decoder, cache key/migration behavior, and changelog together in one release and explicitly override the one-release window; this is simpler after release but breaks older clients and cached data unless separately migrated.

### Option 3

- Option: API-only immediate rename
- Affected impacts: IMP-001, IMP-002, IMP-003
- Trade-off: Change only api/profile.py as narrowly requested; this is the smallest patch but knowingly leaves the iOS decoder, cache, and deprecation documentation inconsistent.
