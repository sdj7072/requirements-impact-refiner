## Change Impact Summary

### Impact IMP-001

- Changed feature: One-hour caching of the dashboard response unit
- Possible issue: A global cache of the full returned mapping can return one tenant's identifier for another tenant and cross the tenant isolation boundary.
- Affected feature or user: Callers of render_dashboard and any tenant whose identifier is included in a cached result
- Trigger: Two different tenant_id values use the same cache entry within the 3,600-second lifetime
- Severity: high
- Prevention or check: Choose an explicit cache unit: key the full result by tenant_id, or cache only tenant-independent body data and reconstruct the tenant field per call.
- Status: blocked

### Impact IMP-002

- Changed feature: Reuse of cached dashboard data
- Possible issue: Returning the same cached dictionary lets one caller's mutation affect later callers and creates shared-state races.
- Affected feature or user: All callers receiving a cache hit
- Trigger: A caller mutates a dictionary that is stored and returned directly from the cache
- Severity: high
- Prevention or check: Cache immutable data or return a new mapping/defensive copy for every call, including cache hits.
- Status: detected

### Impact IMP-003

- Changed feature: A 3,600-second cache lifetime
- Possible issue: Entries may live too long, expire inconsistently, or be refreshed from wall-clock jumps if TTL semantics are implicit.
- Affected feature or user: All dashboard responses served after their first computation
- Trigger: Time crosses the intended one-hour boundary or an implementation uses a non-monotonic/incorrect expiry calculation
- Severity: medium
- Prevention or check: Define TTL as 3,600 seconds from insertion, ensure expired entries are recomputed before return, and test just-before/at/after expiry with a controllable clock.
- Status: refining

### Impact IMP-004

- Changed feature: Cache integration around render_dashboard
- Possible issue: Callers can break if caching changes the function signature, sync behavior, or returned mapping shape.
- Affected feature or user: Any direct or imported caller of render_dashboard
- Trigger: The cache implementation adds required arguments, returns an awaitable, or changes tenant/body fields
- Severity: medium
- Prevention or check: Keep the existing signature and synchronous mapping contract; inject testable cache/clock dependencies without making them required public arguments.
- Status: detected

### Impact IMP-005

- Changed feature: Shared one-hour dashboard cache
- Possible issue: Concurrent misses can cause duplicate work, inconsistent publication, or tenant-key collisions.
- Affected feature or user: Concurrent callers for the same or different tenant keys
- Trigger: Multiple calls observe an absent or expired entry simultaneously
- Severity: medium
- Prevention or check: Use atomic cache publication and tenant-safe keys; at minimum guarantee all concurrent results satisfy current output and mutation-isolation invariants.
- Status: detected

### Impact IMP-006

- Changed feature: Regression coverage for dashboard caching
- Possible issue: A cache can appear correct on a single hit while failing tenant isolation, exact expiry, mutation isolation, or concurrent access.
- Affected feature or user: Maintainers and all dashboard callers
- Trigger: The implementation is planned or shipped without deterministic cache-state and clock-controlled tests
- Severity: medium
- Prevention or check: Add focused tests for miss/hit, different tenants, fresh returned mappings, expiry boundaries, and concurrent misses using a resettable cache and controllable clock.
- Status: detected

## Decision Needed

- Question: What exactly should the one-hour cache store, given that render_dashboard returns tenant-specific data but "dashboard.response" is only the constant body string?

### Option 1

- Option: Cache the full response per tenant_id and return a fresh mapping from the cached immutable value.
- Affected impacts: IMP-001, IMP-002, IMP-005
- Trade-off: Preserves tenant isolation and enables full-result reuse, but creates one cache entry per tenant and requires tenant-safe key normalization.

### Option 2

- Option: Cache only the tenant-independent body value globally for one hour and reconstruct {tenant, body} on every call.
- Affected impacts: IMP-001, IMP-002, IMP-003
- Trade-off: Uses one entry and naturally preserves per-call tenant/mapping behavior, but may provide little benefit because the currently evidenced body computation is only a constant lookup.

### Option 3

- Option: Cache and return the full mutable mapping directly.
- Affected impacts: IMP-001, IMP-002, IMP-005
- Trade-off: Is mechanically smallest but is unsafe without per-tenant keys and changes the current fresh-object behavior; it should be selected only if shared mutation is explicitly acceptable.

## Acceptance and Regression Criteria

### Criterion AC-001

- Observable criterion: For any sequence of calls using tenant IDs A and B, every returned tenant field equals that call's argument; no cache entry can expose A in B's result.

### Criterion AC-002

- Observable criterion: Mutating a mapping returned by one invocation does not change the result of any later invocation, including a cache hit.

### Criterion AC-003

- Observable criterion: A cached value is reusable for less than 3,600 seconds from insertion; at the 3,600-second boundary it is treated as expired and recomputed before being returned.

### Criterion AC-004

- Observable criterion: Existing calls to synchronous render_dashboard(tenant_id) continue to return a mapping with exactly the evidenced tenant and body fields without requiring new arguments.

### Criterion AC-005

- Observable criterion: Concurrent calls for the same and different tenant IDs never publish a result under the wrong key and all returned mappings satisfy tenant and mutation-isolation criteria.
