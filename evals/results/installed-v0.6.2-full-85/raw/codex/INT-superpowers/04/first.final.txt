## Change Impact Summary

### Impact IMP-001

- Changed feature: Cache render_dashboard results for one hour.
- Possible issue: A global cache entry can leak or mislabel tenant-specific responses.
- Affected feature or user: Any caller rendering dashboards for more than one tenant.
- Trigger: A cache hit occurs for a tenant different from the tenant that populated the entry.
- Severity: high
- Prevention or check: Key every full-response cache entry by tenant_id and test interleaved tenants.
- Status: refining

### Impact IMP-002

- Changed feature: Reuse cached dashboard results.
- Possible issue: One caller can mutate a cached dictionary and corrupt later responses, including during concurrent use.
- Affected feature or user: All callers sharing the same tenant cache entry.
- Trigger: A caller mutates a returned dictionary before another cache hit.
- Severity: high
- Prevention or check: Cache immutable payload data or return a fresh copy on every hit, with a mutation-isolation test.
- Status: refining

### Impact IMP-003

- Changed feature: Expire dashboard cache entries after one hour.
- Possible issue: Entries may expire early, remain stale past one hour, or behave nondeterministically at the boundary.
- Affected feature or user: Callers expecting the approved one-hour freshness window.
- Trigger: Time reaches or crosses the entry's expiry timestamp, or the system wall clock changes.
- Severity: medium
- Prevention or check: Define 3600 seconds precisely, use a monotonic/injectable clock for local expiry, and test just-before, at, and after expiry.
- Status: refining

### Impact IMP-004

- Changed feature: Store tenant-scoped cached dashboard responses.
- Possible issue: A process-local cache behaves independently per worker, while a shared backend adds availability and configuration behavior not present in the repository.
- Affected feature or user: Deployments with multiple processes or hosts and operators responsible for cache health.
- Trigger: The service runs in more than one process/host or the selected cache backend is unavailable.
- Severity: high
- Prevention or check: Choose process-local or shared topology explicitly before planning and document its consistency and failure semantics.
- Status: blocked

### Impact IMP-005

- Changed feature: Retain one cache entry per active tenant for up to one hour.
- Possible issue: High tenant cardinality or stale entries can cause unbounded memory or backend growth.
- Affected feature or user: Service processes or the selected shared cache backend.
- Trigger: Many distinct tenant IDs render dashboards within or across expiry windows.
- Severity: medium
- Prevention or check: Define capacity and eviction/expired-entry cleanup appropriate to the selected topology and verify expired entries are reclaimable.
- Status: refining

### Impact IMP-006

- Changed feature: Introduce stateful, time-dependent behavior into render_dashboard.
- Possible issue: Unknown callers may depend on fresh objects or deployment-specific behavior, and cache regressions may go undetected.
- Affected feature or user: Unseen route/controller consumers and the eventual test suite.
- Trigger: Implementation begins without the missing application/test context or equivalent acceptance tests.
- Severity: high
- Prevention or check: Locate or supply the integration repository and add deterministic tests for hits, tenant isolation, mutation isolation, expiry, and selected-backend failure behavior.
- Status: blocked

## Decision Needed

- Question: Which cache topology should the one-hour tenant-scoped dashboard cache use?

### Option 1

- Option: Process-local per-tenant TTL cache
- Affected impacts: IMP-004, IMP-005, IMP-002
- Trade-off: Adds no external dependency and fits the visible repository, but each worker has independent entries and expiry, duplicate recomputation, and per-process memory.

### Option 2

- Option: Shared per-tenant TTL cache backend
- Affected impacts: IMP-004, IMP-005, IMP-001
- Trade-off: Provides cross-worker reuse and centrally enforced expiry, but requires a new backend, serialization, configuration, availability/failure semantics, and integration evidence absent from this repository.
