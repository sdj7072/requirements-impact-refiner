## Change Impact Summary

### Impact IMP-001

- Changed feature: One-hour caching of the dashboard response
- Possible issue: A shared full-response cache can reuse the first tenant's payload for other tenants.
- Affected feature or user: Any consumer calling render_dashboard for more than one tenant
- Trigger: The complete returned mapping is cached under a static dashboard.response key.
- Severity: high
- Prevention or check: Select a tenant-independent cache unit or include tenant_id in every full-response cache key.
- Status: blocked

### Impact IMP-002

- Changed feature: Reuse of a cached dashboard value
- Possible issue: Callers may observe mutations made through a previously returned cached dict.
- Affected feature or user: All callers sharing a cached entry
- Trigger: render_dashboard returns the cached mutable mapping by reference.
- Severity: high
- Prevention or check: Cache only immutable body data or return a newly constructed/copy-isolated mapping on every call.
- Status: blocked

### Impact IMP-003

- Changed feature: A 3,600-second dashboard cache lifetime
- Possible issue: Entries can expire too early, remain stale beyond one hour, or be refreshed inconsistently.
- Affected feature or user: Dashboard users around the expiration boundary
- Trigger: TTL measurement and expiration behavior are left implicit.
- Severity: medium
- Prevention or check: Define a 3,600-second TTL using an injectable monotonic clock and test hits immediately before and recomputation at or after expiry.
- Status: refining

### Impact IMP-004

- Changed feature: Storage and lifecycle of one-hour cached entries
- Possible issue: Per-process caches can diverge or grow without bounds, while a shared backend can introduce configuration and availability failures.
- Affected feature or user: Runtime instances and dashboard availability
- Trigger: A backend is chosen without defining process scope, eviction, bounds, and failure behavior.
- Severity: medium
- Prevention or check: Select the backend scope explicitly and require bounded storage plus a defined cache-failure fallback.
- Status: blocked

### Impact IMP-005

- Changed feature: Caching behavior in render_dashboard
- Possible issue: Cross-tenant reuse, shared mutation, or incorrect expiry can ship undetected.
- Affected feature or user: All dashboard callers
- Trigger: The cache is implemented without a new deterministic test harness.
- Severity: medium
- Prevention or check: The planning owner must select a Python test framework and add deterministic tenant, mutation, hit, expiry, and failure tests before implementation is accepted.
- Status: deferred

## Decision Needed

- Question: Which cache unit and runtime scope should the one-hour dashboard cache use?

### Option 1

- Option: Cache only the tenant-independent body and build a fresh tenant envelope on every call.
- Affected impacts: IMP-001, IMP-002, IMP-004
- Trade-off: Safest tenant and mutation semantics with the least repository change, but caching the current constant body provides little performance benefit and remains process-local unless a shared backend is later introduced.

### Option 2

- Option: Cache the complete response per tenant in an in-process bounded TTL cache.
- Affected impacts: IMP-001, IMP-002, IMP-003, IMP-004
- Trade-off: Can avoid repeated per-tenant rendering without external infrastructure, but every process has independent entries and the implementation must copy results, bound memory, and key by tenant.

### Option 3

- Option: Cache the complete response per tenant in a shared cache backend.
- Affected impacts: IMP-001, IMP-002, IMP-003, IMP-004
- Trade-off: Provides cross-process reuse and consistent TTL scope, but requires a new dependency/configuration contract plus serialization, availability, and fallback handling absent from this repository.
