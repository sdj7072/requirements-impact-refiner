## Change Impact Summary

### Impact IMP-001

- Changed feature: One-hour caching of dashboard.response
- Possible issue: Caching the wrong boundary can change the returned object semantics or make tenant-specific data stale as a unit.
- Affected feature or user: render_dashboard callers and the response objects they receive
- Trigger: A cache hit after a prior render_dashboard call
- Severity: high
- Prevention or check: Choose explicitly between caching the immutable body and caching a tenant-keyed full response with copy-on-read.
- Status: blocked

### Impact IMP-002

- Changed feature: Reuse of cached dashboard responses
- Possible issue: A global full-response cache could expose a cached tenant identifier to a different tenant.
- Affected feature or user: Every caller that renders dashboards for more than one tenant
- Trigger: A full-response cache hit for a tenant different from the cache-filling tenant
- Severity: critical
- Prevention or check: Cache only tenant-independent body data, or include tenant_id in the cache key and verify cross-tenant misses.
- Status: detected

### Impact IMP-003

- Changed feature: Caching of render_dashboard output
- Possible issue: One caller's mutation of a cached dictionary could affect later callers.
- Affected feature or user: Callers that modify the returned dictionary
- Trigger: The same cached dictionary object is returned more than once
- Severity: high
- Prevention or check: Keep constructing a fresh envelope, or copy a tenant-keyed cached response before returning it.
- Status: detected

### Impact IMP-004

- Changed feature: One-hour cache lifetime
- Possible issue: Entries may survive beyond one hour, expire inconsistently, or refresh concurrently in an undefined way.
- Affected feature or user: Dashboard requests around cache expiry and concurrent first requests
- Trigger: The one-hour boundary or simultaneous cache misses
- Severity: medium
- Prevention or check: Define TTL as 3600 seconds using an injectable monotonic clock and require thread-safe cache access or explicitly tolerate duplicate computation.
- Status: detected

### Impact IMP-005

- Changed feature: New process-level cache state
- Possible issue: Expiry, tenant isolation, and mutable-object regressions could ship without detection, and process restart behavior may be misunderstood.
- Affected feature or user: Deployment behavior and maintainers validating the cache
- Trigger: Implementation without a declared cache owner or focused tests
- Severity: medium
- Prevention or check: Keep the cache local and dependency-free unless broader infrastructure is supplied, and add deterministic unit coverage for hit, miss, expiry, tenant isolation, and returned-object isolation.
- Status: detected

## Decision Needed

- Question: What exact value should the approved one-hour dashboard cache store?

### Option 1

- Option: Cache only the immutable RESPONSE/body value and continue building a fresh tenant-specific dictionary on every call.
- Affected impacts: IMP-001, IMP-002, IMP-003, IMP-004
- Trade-off: Best preserves current tenant and mutation semantics, but caching the current constant offers little performance benefit until body generation becomes expensive.

### Option 2

- Option: Cache the complete response per tenant_id and return a copy on every hit.
- Affected impacts: IMP-001, IMP-002, IMP-003, IMP-004, IMP-005
- Trade-off: Can avoid full response generation while preserving isolation, but creates per-tenant state, key-cardinality, copying, expiry, and concurrency obligations.

### Option 3

- Option: Cache and return the complete response object per tenant_id without copying.
- Affected impacts: IMP-001, IMP-002, IMP-003, IMP-004, IMP-005
- Trade-off: Has the least per-hit work but breaks the current fresh-object invariant and risks cross-call mutation, so it requires an explicit interface change.
