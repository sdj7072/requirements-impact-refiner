## Change Impact Summary

### Impact IMP-001

- Changed feature: Reconnect replay of offline.edits
- Possible issue: An edit replayed after its target's tombstone has expired can recreate data that the server previously deleted.
- Affected feature or user: Users and server records involved in delete-versus-offline-edit conflicts.
- Trigger: A client remains offline longer than 24 hours and later replays an edit for a deleted record.
- Severity: critical
- Prevention or check: Choose and enforce an explicit late-edit policy, with a test covering replay just inside and just outside the retention window.
- Status: blocked

### Impact IMP-002

- Changed feature: Routing queued edits through models/record.py
- Possible issue: Replay-time updated_at values can replace the edits' original chronology and alter last-write-wins outcomes.
- Affected feature or user: Records with concurrent server changes or multiple offline edits.
- Trigger: Queued edits are stamped when replayed after reconnect.
- Severity: high
- Prevention or check: Keep queue order as the replay sequence, distinguish local creation metadata from server updated_at, and test concurrent-update ordering.
- Status: detected

### Impact IMP-003

- Changed feature: Automatic reconnect synchronization
- Possible issue: A disconnect during replay can apply an edit twice or drop remaining edits if acknowledgement and dequeue timing are not atomic.
- Affected feature or user: Clients reconnecting over unstable networks and records receiving replayed edits.
- Trigger: Connectivity fails after a server write but before the client records acknowledgement.
- Severity: high
- Prevention or check: Give queued edits stable identities, acknowledge each successful application, dequeue only acknowledged edits, and verify retry idempotency.
- Status: detected

## Decision Needed

- Question: What should happen when an offline edit is replayed after the target record's 24-hour tombstone has expired?

### Option 1

- Option: Reject and surface a conflict
- Affected impacts: IMP-001
- Trade-off: Prevents silent resurrection but requires a client-visible conflict/recovery path.

### Option 2

- Option: Extend tombstone retention
- Affected impacts: IMP-001
- Trade-off: Allows more offline clients to sync safely but increases server storage and still needs a finite cutoff policy.

### Option 3

- Option: Allow recreation
- Affected impacts: IMP-001
- Trade-off: Keeps replay simple but can silently undo a server-side deletion.
