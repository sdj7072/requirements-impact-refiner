## Change Impact Summary

### Impact IMP-001

- Changed feature: One-hour caching of dashboard.response
- Possible issue: A shared cache key can return one tenant's response to another tenant.
- Affected feature or user: All dashboard tenants and their data isolation.
- Trigger: Two tenants render dashboard.response while the same cache entry remains live.
- Severity: critical
- Prevention or check: Include tenant_id in every cache key and test that tenants never share entries.
- Status: refining

### Impact IMP-002

- Changed feature: Serving dashboard responses for up to one hour
- Possible issue: A user may continue receiving data based on obsolete permissions after a role change.
- Affected feature or user: Users whose roles or permissions change and tenants containing them.
- Trigger: A role changes before the cached dashboard response expires.
- Severity: critical
- Prevention or check: Evict or version affected tenant/dashboard entries as part of the role-change invalidation path.
- Status: refining

### Impact IMP-003

- Changed feature: One-hour dashboard response cache
- Possible issue: Dashboard changes may remain invisible until TTL expiry.
- Affected feature or user: Tenants whose dashboard content changes.
- Trigger: dashboard.updated is published while a cached response exists.
- Severity: high
- Prevention or check: Consume the event and invalidate the affected tenant entry; define payload tenant identity and idempotent handling.
- Status: refining

### Impact IMP-004

- Changed feature: Adding cached mutable state
- Possible issue: Process-local entries can diverge across workers and ignore invalidations delivered elsewhere.
- Affected feature or user: Multi-worker or multi-instance deployments.
- Trigger: More than one process serves the same tenant or receives different invalidation events.
- Severity: high
- Prevention or check: Choose a shared cache/event strategy, or explicitly constrain and test a single-process local cache.
- Status: blocked

### Impact IMP-005

- Changed feature: Caching render results
- Possible issue: Concurrent misses may race, duplicate work, or mutate shared cached objects.
- Affected feature or user: Concurrent requests for the same tenant.
- Trigger: Two requests miss the same tenant entry simultaneously or callers mutate a returned mapping.
- Severity: medium
- Prevention or check: Use safe cache access and return immutable/copy-isolated values; cover concurrent or re-entrant access.
- Status: refining

## Decision Needed

- Question: Which cache scope should own the one-hour dashboard entries and their invalidation?

### Option 1

- Option: Shared cache with tenant-scoped keys and event-driven invalidation
- Affected impacts: IMP-004, IMP-002, IMP-003, IMP-001
- Trade-off: Correct across workers and instances, but requires a shared cache/client and event plumbing that this repository does not currently define.

### Option 2

- Option: Process-local in-memory cache, explicitly limited to a single-process deployment
- Affected impacts: IMP-004, IMP-005, IMP-002, IMP-003
- Trade-off: Can be implemented with the standard library now, but each worker has independent state and invalidation is only reliable within one process.

### Option 3

- Option: Tenant generation/version keys backed by an existing shared store
- Affected impacts: IMP-004, IMP-002, IMP-003
- Trade-off: Avoids broad eviction and tolerates retries, but needs a shared authoritative version store whose API is not present in the repository.
