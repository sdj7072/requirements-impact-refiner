## Change Impact Summary

### Impact IMP-001

- Changed feature: One-hour dashboard.response caching
- Possible issue: A cache key that omits tenant_id could return one tenant's dashboard to another tenant.
- Affected feature or user: All callers of api.dashboard.render.
- Trigger: Two tenants render dashboards while a shared cache entry is populated.
- Severity: critical
- Prevention or check: Key every cached dashboard response by tenant_id and verify tenant isolation in tests.
- Status: detected

### Impact IMP-002

- Changed feature: One-hour dashboard.response caching
- Possible issue: A role change could leave authorization-sensitive dashboard content visible for up to one hour.
- Affected feature or user: Tenants whose user roles or permissions change.
- Trigger: A role change occurs after a dashboard response has been cached.
- Severity: critical
- Prevention or check: Select and implement a dashboard-cache invalidation policy for role changes.
- Status: blocked

### Impact IMP-003

- Changed feature: One-hour dashboard.response caching
- Possible issue: Dashboard updates could remain invisible until the TTL expires.
- Affected feature or user: Tenants with dashboard changes during the cache lifetime.
- Trigger: dashboard.updated is published after a response has been cached.
- Severity: high
- Prevention or check: Select whether dashboard.updated invalidates the affected tenant's cache entry.
- Status: blocked

### Impact IMP-004

- Changed feature: In-memory response reuse
- Possible issue: Concurrent callers could observe inconsistent entries or populate duplicate values.
- Affected feature or user: Concurrent requests for the same tenant.
- Trigger: Multiple requests arrive around cache miss, expiry, or invalidation.
- Severity: medium
- Prevention or check: Use a cache abstraction with atomic get/set/delete semantics and test expiry and invalidation boundaries.
- Status: detected

## Decision Needed

- Question: Which events must invalidate the one-hour tenant-scoped dashboard cache?

### Option 1

- Option: Invalidate on both role changes and dashboard.updated
- Affected impacts: IMP-002, IMP-003
- Trade-off: Safest freshness and authorization behavior, with additional invalidation wiring.

### Option 2

- Option: Invalidate only on role changes
- Affected impacts: IMP-002, IMP-003
- Trade-off: Protects permission changes, but ordinary dashboard updates may remain stale for up to one hour.

### Option 3

- Option: Use TTL only
- Affected impacts: IMP-002, IMP-003
- Trade-off: Smallest implementation, but both permission and dashboard changes may be stale for up to one hour.
