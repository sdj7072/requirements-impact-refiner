## Change Impact Summary

### Impact IMP-001

- Changed feature: One-hour caching of dashboard.response
- Possible issue: A user whose role changes could receive an authorization-stale dashboard until TTL expiry.
- Affected feature or user: Users and tenants whose dashboard visibility depends on roles.
- Trigger: A role changes while a tenant dashboard response is cached.
- Severity: critical
- Prevention or check: Invalidate the affected tenant's dashboard cache from the existing role-change invalidation path, or explicitly accept the stale-access window.
- Status: blocked

### Impact IMP-002

- Changed feature: One-hour caching of dashboard.response
- Possible issue: Dashboard updates could remain invisible for up to one hour.
- Affected feature or user: Readers of an updated tenant dashboard.
- Trigger: dashboard.updated is published while that tenant's response is cached.
- Severity: high
- Prevention or check: Evict the affected tenant's entry when dashboard.updated is handled, or explicitly accept TTL-only freshness.
- Status: blocked

## Decision Needed

- Question: Which invalidation policy should the one-hour dashboard cache use?

### Option 1

- Option: Invalidate per tenant on both role changes and dashboard.updated (recommended)
- Affected impacts: IMP-001, IMP-002
- Trade-off: Strongest correctness and tenant isolation; requires wiring both existing invalidation signals to the new cache.

### Option 2

- Option: Invalidate only on dashboard.updated
- Affected impacts: IMP-001, IMP-002
- Trade-off: Keeps content fresh but can expose authorization-stale dashboards for up to one hour after role changes.

### Option 3

- Option: Use TTL only
- Affected impacts: IMP-001, IMP-002
- Trade-off: Smallest implementation, but accepts up to one hour of stale permissions and dashboard content.
