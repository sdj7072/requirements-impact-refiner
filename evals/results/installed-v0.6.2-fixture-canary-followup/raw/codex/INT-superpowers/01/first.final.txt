## Change Impact Summary

### Impact IMP-001

- Changed feature: A one-hour cache is introduced for dashboard responses.
- Possible issue: If the cache is global or keyed incompletely, one tenant can receive a response labeled or populated for another tenant.
- Affected feature or user: All callers rendering dashboards for more than one tenant, with a potential cross-tenant privacy breach.
- Trigger: Two different tenant_id values access the cache during the same entry lifetime.
- Severity: high
- Prevention or check: Key every entry by the complete tenant identity and verify isolation with alternating-tenant and concurrent-tenant tests.
- Status: detected

### Impact IMP-002

- Changed feature: A rendered dashboard response may be reused for one hour.
- Possible issue: Entries can outlive the intended 3,600-second bound or refresh inconsistently if TTL start, expiry, and clock behavior are unspecified.
- Affected feature or user: Dashboard users who expect updates to appear after the approved cache window.
- Trigger: A request arrives at or after an entry's expiration boundary, or the runtime clock changes.
- Severity: medium
- Prevention or check: Define TTL from successful insertion using a monotonic clock where applicable, treat age &gt;= 3,600 seconds as expired, and cover the exact boundary with a controllable clock.
- Status: detected

### Impact IMP-003

- Changed feature: The renderer's result is retained and reused instead of reconstructed on every call.
- Possible issue: A caller mutation can contaminate subsequent responses if the same cached dictionary instance is returned.
- Affected feature or user: Later dashboard requests for the same tenant and any code that assumes an independent return value.
- Trigger: A caller mutates a returned dictionary before another cache hit.
- Severity: high
- Prevention or check: Cache an immutable representation or return a fresh copy on every hit and miss; add a mutation-isolation regression test.
- Status: detected

### Impact IMP-004

- Changed feature: render_dashboard gains time-based shared state.
- Possible issue: Workers can serve inconsistent cache generations, duplicate expensive refreshes, or block/fail requests differently depending on cache topology.
- Affected feature or user: Concurrent dashboard requests and multi-worker deployments.
- Trigger: Concurrent misses, expiration, worker restart, or cache-backend failure.
- Severity: high
- Prevention or check: Choose per-process or shared caching explicitly, then define miss coalescing, atomic publication, and fail-open rendering behavior appropriate to that choice.
- Status: blocked

### Impact IMP-005

- Changed feature: The source of render_dashboard's return value changes from immediate construction to cached retrieval.
- Possible issue: Caching can alter the return shape, tenant labeling, object independence, or error timing observed by callers.
- Affected feature or user: Every direct or indirect consumer of render_dashboard.
- Trigger: A cache hit, miss, expiration, or backend error follows a different return path.
- Severity: medium
- Prevention or check: Keep the public signature and mapping contents unchanged and run the same contract assertions through hit, miss, expiry, and failure paths.
- Status: detected

### Impact IMP-006

- Changed feature: Dashboard rendering begins depending on cache state and expiration.
- Possible issue: Cache failures or pathological misses can become request failures or remain invisible in production.
- Affected feature or user: Operators and users during cache outage, restart, or elevated miss rates.
- Trigger: The selected cache cannot be read or written, entries churn, or workers restart.
- Severity: medium
- Prevention or check: Render on cache failure, avoid caching failed results, and expose hit, miss, expiry, refresh, and error signals compatible with the selected topology.
- Status: refining

## Decision Needed

- Question: Which cache topology should writing-plans treat as the approved repository boundary?

### Option 1

- Option: Per-process, tenant-keyed in-memory cache
- Affected impacts: IMP-004, IMP-006
- Trade-off: Adds no infrastructure and fits the current tiny repository, but each worker has independent entries and refresh timing; restarts cold-start the cache.

### Option 2

- Option: Shared, tenant-keyed cache
- Affected impacts: IMP-004, IMP-006
- Trade-off: Provides cross-worker reuse and more consistent generations, but adds a backend, serialization, network-failure behavior, configuration, and operational ownership.
