## Decision Needed

| Question | Option | Impact IDs | Trade-off |
| --- | --- | --- | --- |
| Which freshness and permission-invalidation policy should govern the one-hour dashboard cache? | Tenant plus write-event invalidation: key by `tenant_id`, expire after 3,600 seconds, evict the affected tenant on `dashboard.updated`, and leave role-change behavior unchanged. | `IMP-001`, `IMP-002`, `IMP-003` | Uses the supplied dependency and event with good write freshness, but is safe only if dashboard output is not permission-dependent or authorization is reapplied after lookup. |
| Which freshness and permission-invalidation policy should govern the one-hour dashboard cache? | Permission-safe invalidation: use tenant-scoped caching and `dashboard.updated` eviction, and also evict or version dashboard entries when roles change. | `IMP-001`, `IMP-002`, `IMP-003` | Covers permission-dependent output, but broadens the role-change path and may reduce cache hit rate. |
| Which freshness and permission-invalidation policy should govern the one-hour dashboard cache? | TTL only: key by `tenant_id`, expire after 3,600 seconds, and add no event-driven dashboard invalidation. | `IMP-001`, `IMP-002`, `IMP-003` | Smallest mechanism, but dashboard writes can remain stale for up to an hour and permission freshness remains unproven. |
