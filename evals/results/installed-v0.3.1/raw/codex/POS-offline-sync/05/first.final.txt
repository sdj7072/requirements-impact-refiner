## Decision Needed

| Question | Option | Impact IDs | Trade-off |
| --- | --- | --- | --- |
| When a queued local mutation targets a record changed or deleted on the server since the client last saw it, which conflict policy should reconnect sync use? | Detect and surface conflicts: apply automatically only when the server version still matches the queued mutation's base version; never auto-resurrect a tombstoned record. | `IMP-001`, `IMP-002`, `IMP-003`, `IMP-005` | Best protection against silent data loss, but requires capturing a base version and providing a conflict-resolution path. |
| When a queued local mutation targets a record changed or deleted on the server since the client last saw it, which conflict policy should reconnect sync use? | Server wins: discard the queued local mutation when the server changed or deleted the record. | `IMP-001`, `IMP-002`, `IMP-003` | Simplest deterministic policy and respects deletions, but can silently lose offline work unless the app preserves or reports rejected edits. |
| When a queued local mutation targets a record changed or deleted on the server since the client last saw it, which conflict policy should reconnect sync use? | Client wins for updates, but an unexpired server tombstone wins over local edits. | `IMP-001`, `IMP-002`, `IMP-003`, `IMP-005` | Preserves more offline edits, but may overwrite newer remote changes and remains unsafe after tombstone expiry without a durable deletion version. |
