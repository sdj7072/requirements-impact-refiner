## Decision Needed

| Question | Option | Impact IDs | Trade-off |
| --- | --- | --- | --- |
| Which authority should resolve queued offline edits that conflict with server updates or deletions? | Server-authoritative conditional replay (recommended): compare the queued edit’s base version with current server state, reject or surface stale edits, let tombstones win, and require durable deletion knowledge or rejection of unknown formerly known IDs after tombstone expiry. | `IMP-001`, `IMP-002`, `IMP-003`, `IMP-004`, `IMP-005`, `IMP-006` | Best protection against silent overwrite and resurrection, but requires base-version metadata, idempotent mutation identity, and server support for post-expiry deletion recognition or explicit rejection. |
| Which authority should resolve queued offline edits that conflict with server updates or deletions? | Timestamp last-write-wins: compare edit and server `updated_at`, treating a present tombstone as another timestamped version. | `IMP-001`, `IMP-002`, `IMP-003`, `IMP-004`, `IMP-005` | Automates most conflicts, but correctness depends on timestamp authority and tie rules and cannot by itself recognize a deletion after its 24-hour tombstone expires. |
| Which authority should resolve queued offline edits that conflict with server updates or deletions? | Client-authoritative replay: apply queued edits in local creation order, including recreating a missing record. | `IMP-001`, `IMP-002`, `IMP-003`, `IMP-004`, `IMP-006` | Maximizes preservation of offline intent, but can overwrite newer server state and resurrect deliberately deleted records. |
