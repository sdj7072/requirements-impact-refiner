| Question | Option | Impact IDs | Trade-off |
| --- | --- | --- | --- |
| Which compatibility policy should govern the one-version deprecation window? | **Recommended:** Expose `name` as canonical, retain deprecated `displayName`, accept both with `name` precedence, and persist both cache keys until the next version. | `IMP-001`, `IMP-002`, `IMP-003`, `IMP-004`, `IMP-005` | Strongest upgrade and rollback compatibility, with duplicate fields for one release. |
| Which compatibility policy should govern the one-version deprecation window? | Expose both API fields and accept both, but write only `name` to cache. | `IMP-001`, `IMP-002`, `IMP-003`, `IMP-004`, `IMP-005` | Simpler cache end state, but rollback may fail after the cache is rewritten. |
| Which compatibility policy should govern the one-version deprecation window? | Keep `displayName` as a permanent read alias while emitting and persisting only `name` after one version. | `IMP-001`, `IMP-002`, `IMP-003`, `IMP-004`, `IMP-005` | Maximizes forward reads but retains legacy handling indefinitely and does not protect old readers of new data. |
