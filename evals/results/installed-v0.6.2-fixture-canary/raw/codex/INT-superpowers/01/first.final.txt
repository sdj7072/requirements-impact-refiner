## Change Impact Summary

### Impact IMP-001

- Changed feature: Caching the complete render_dashboard result
- Possible issue: A cache entry reused across tenant IDs could return the wrong tenant envelope and create a cross-tenant data boundary failure.
- Affected feature or user: All callers of render_dashboard and any tenant-scoped dashboard consumer.
- Trigger: Two distinct tenant_id values resolve to the same cache entry.
- Severity: critical
- Prevention or check: If the full response is cached, include a canonical tenant_id in the cache key and test alternating and concurrent tenants; otherwise cache only the shared body.
- Status: refining

### Impact IMP-002

- Changed feature: One-hour reuse of the dashboard response
- Possible issue: Entries may live for the wrong duration, never expire, or refresh at an unintended boundary.
- Affected feature or user: Dashboard callers relying on the approved one-hour freshness window.
- Trigger: A request occurs before, at, or after 3,600 seconds from cache population.
- Severity: high
- Prevention or check: Define the TTL as exactly 3,600 seconds from successful population and verify reuse before expiry plus refresh after expiry with a controllable clock.
- Status: refining

### Impact IMP-003

- Changed feature: Selection of the value stored in the one-hour cache
- Possible issue: Planning the wrong cache unit could either fail to cache the intended work or accidentally cache tenant-specific state as shared state.
- Affected feature or user: render_dashboard's implementation, cache keys, and tests.
- Trigger: Implementation begins without deciding whether dashboard.response means the full returned mapping or only RESPONSE/body.
- Severity: high
- Prevention or check: Choose one of the mutually exclusive cache units before writing-plans and keep the existing function signature and return shape.
- Status: refining

### Impact IMP-004

- Changed feature: Concurrent population and refresh of cache entries
- Possible issue: Simultaneous misses or expiry may perform duplicate population, expose partial state, or cache failures depending on the selected backend.
- Affected feature or user: Concurrent dashboard requests for the same cache key.
- Trigger: Two or more callers miss or refresh the same entry at once.
- Severity: medium
- Prevention or check: Require atomic publication of only successful complete values; document whether duplicate computation is acceptable and test same-key concurrency against the chosen cache mechanism.
- Status: detected

### Impact IMP-005

- Changed feature: Runtime ownership of the one-hour cache
- Possible issue: A process-local cache may provide inconsistent hit rates across workers, grow without bounds by tenant, or retain entries across an unintended lifecycle.
- Affected feature or user: Deployment workers, memory usage, observability, and cache reset behavior.
- Trigger: The service runs multiple workers, receives many distinct tenant IDs, restarts, or needs emergency invalidation.
- Severity: medium
- Prevention or check: Writing-plans must identify the existing cache/backend convention or explicitly bound a process-local cache, define startup/restart behavior, and add hit/miss/expiry observability appropriate to the repository.
- Status: detected

### Impact IMP-006

- Changed feature: Cached behavior replacing unconditional response construction
- Possible issue: Contract, tenant isolation, TTL boundary, and concurrency regressions could ship undetected.
- Affected feature or user: render_dashboard consumers and future cache maintenance.
- Trigger: The cache implementation changes return values or timing behavior without focused automated checks.
- Severity: high
- Prevention or check: Add tests for unchanged response shape, distinct tenants, hit reuse, 3,600-second expiry, failed population, and concurrent same-key access using deterministic time and isolated cache state.
- Status: detected

## Decision Needed

- Question: What exactly should the approved one-hour dashboard cache store?

### Option 1

- Option: Cache each complete render_dashboard result under a tenant-scoped key.
- Affected impacts: IMP-001, IMP-002, IMP-003, IMP-004, IMP-005, IMP-006
- Trade-off: Caches the full response as users likely experience it, but requires canonical tenant keys, bounded entry lifecycle, concurrency semantics, and strict cross-tenant tests.

### Option 2

- Option: Cache only the shared RESPONSE/body value and construct the tenant envelope on every call.
- Affected impacts: IMP-002, IMP-003, IMP-005, IMP-006
- Trade-off: Avoids storing tenant-specific response objects and preserves tenant isolation by construction, but the current body is a constant so the cache adds complexity with negligible work saved.
