## Change Impact Summary

### Impact IMP-001

- Changed feature: One-hour caching of the rendered dashboard value
- Possible issue: A cache key that omits tenant_id can serve a response carrying the wrong tenant identifier.
- Affected feature or user: Dashboard consumers and tenant data isolation
- Trigger: Requests for different tenants share a cached full response.
- Severity: high
- Prevention or check: Either key the full response by tenant_id or cache only tenant-neutral body data and rebuild the tenant envelope for every call.
- Status: refining

### Impact IMP-002

- Changed feature: A 3,600-second dashboard cache lifetime
- Possible issue: Entries may live longer or shorter than intended, refresh on access unexpectedly, or lack deterministic expiration.
- Affected feature or user: Dashboard freshness and repeated-request behavior
- Trigger: A request occurs at or near the one-hour boundary.
- Severity: high
- Prevention or check: Define fixed 3,600-second expiry from cache insertion using an injectable or controllable clock, and test before, at, and after expiry.
- Status: refining

### Impact IMP-003

- Changed feature: Reuse of cached dashboard data
- Possible issue: A caller can mutate a shared cached dictionary and corrupt later responses.
- Affected feature or user: All in-process callers of render_dashboard
- Trigger: The cache stores and returns the same mutable dictionary object.
- Severity: medium
- Prevention or check: Cache an immutable tenant-neutral value or return a fresh copy/envelope on every call.
- Status: refining

### Impact IMP-004

- Changed feature: Stateful reuse of dashboard results for one hour
- Possible issue: Concurrent misses can duplicate work, and process-local caches can disagree across workers or grow without bounds.
- Affected feature or user: Runtime workers, memory use, and cache consistency
- Trigger: Simultaneous requests, multiple worker processes, or many tenant keys
- Severity: medium
- Prevention or check: Select an explicit local or shared backend, define atomic fill/locking expectations and bounded eviction, and document accepted multi-worker behavior.
- Status: refining

### Impact IMP-005

- Changed feature: A new runtime cache dependency or in-memory cache
- Possible issue: Backend failures may break the dashboard, and cache effectiveness or expiry failures may be invisible.
- Affected feature or user: Dashboard availability and operators
- Trigger: Cache read/write errors, unavailable shared infrastructure, or ineffective caching
- Severity: medium
- Prevention or check: Specify fail-open behavior to recompute the current response, plus minimal hit/miss/error observability appropriate to the selected backend.
- Status: refining

### Impact IMP-006

- Changed feature: One-hour cache behavior around render_dashboard
- Possible issue: Incorrect keying, expiration, object reuse, or fallback can ship without detection.
- Affected feature or user: Dashboard correctness across tenants and over time
- Trigger: The cache implementation changes without executable boundary tests.
- Severity: high
- Prevention or check: Add deterministic tests for same/different tenants, cache hits, the 3,600-second boundary, independent returned objects, concurrent misses as applicable, and cache failure fallback.
- Status: refining

## Decision Needed

- Question: Which cache boundary and backend should the approved one-hour dashboard cache use?

### Option 1

- Option: Cache the full rendered dictionary in process memory, keyed by tenant_id, for 3,600 seconds, returning a fresh copy per call.
- Affected impacts: IMP-001, IMP-002, IMP-003, IMP-004, IMP-005, IMP-006
- Trade-off: Smallest repository change and no external dependency, but each worker has an independent cache and memory/eviction plus duplicate-fill behavior must be bounded.

### Option 2

- Option: Cache the full rendered dictionary in a shared backend, keyed by tenant_id, for 3,600 seconds, returning a deserialized fresh value per call.
- Affected impacts: IMP-001, IMP-002, IMP-003, IMP-004, IMP-005, IMP-006
- Trade-off: Consistent across workers and deployments, but requires backend selection, dependencies, configuration, serialization, failure handling, and operational ownership absent from this repository.

### Option 3

- Option: Cache only the tenant-neutral RESPONSE body for 3,600 seconds and construct a fresh tenant dictionary on every call.
- Affected impacts: IMP-001, IMP-002, IMP-003, IMP-004, IMP-005, IMP-006
- Trade-off: Preserves tenant isolation and fresh-object behavior with one global entry, but the current body is already a module constant, so this adds state with no demonstrated performance benefit and may not satisfy the intended full-response cache.
