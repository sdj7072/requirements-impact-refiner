## Change Impact Summary

### Impact IMP-001

- Changed feature: Webhook delivery retries after provider timeout
- Possible issue: An ambiguous timeout can cause the same logical webhook delivery to be attempted again after the provider already accepted it, producing duplicate consumer-visible effects.
- Affected feature or user: Webhook consumers and downstream state changed by webhook handlers
- Trigger: The provider accepts or processes a delivery but the caller observes a timeout and retry_delivery issues another attempt.
- Severity: high
- Prevention or check: Select and implement a documented idempotency or no-retry strategy, then verify one consumer-visible effect per logical delivery.
- Status: blocked

### Impact IMP-002

- Changed feature: Concurrent execution of retry_delivery
- Possible issue: Two workers can race and both deliver the same event if duplicate detection is absent or non-atomic.
- Affected feature or user: Retry workers, the delivery provider, and webhook consumers
- Trigger: Multiple retry attempts for the same logical event overlap after a timeout or redelivery.
- Severity: high
- Prevention or check: Make the selected duplicate-protection operation atomic and test simultaneous attempts for the same delivery identity.
- Status: blocked

### Impact IMP-003

- Changed feature: Delivery identity and duplicate-retention semantics introduced by safer retries
- Possible issue: An unstable or overly broad key can suppress legitimate events, while a short or undocumented retention window can allow late duplicates.
- Affected feature or user: Webhook producers, retry operators, consumers, and replay/backfill workflows
- Trigger: The implementation classifies attempts as the same logical delivery or expires duplicate-protection state.
- Severity: medium
- Prevention or check: Document the key source, scope, retention window, replay policy, and behavior when identity is missing before implementation.
- Status: blocked

## Decision Needed

- Question: Which duplicate-protection contract should govern retry_delivery after an ambiguous provider timeout?

### Option 1

- Option: Persist a stable logical-delivery idempotency key locally and atomically claim it before delivery.
- Affected impacts: IMP-001, IMP-002, IMP-003
- Trade-off: Provides strong local control and concurrency safety, but requires durable state, key and retention definitions, cleanup, and failure-recovery behavior.

### Option 2

- Option: Require and pass through a documented provider-native idempotency key and guarantee.
- Affected impacts: IMP-001, IMP-002, IMP-003
- Trade-off: Avoids local deduplication state, but safety depends on verified provider semantics, key propagation, retention, and behavior during provider outages.

### Option 3

- Option: Do not automatically retry when the provider outcome is ambiguous.
- Affected impacts: IMP-001, IMP-002
- Trade-off: Avoids retry-created duplicates, but can lose deliveries when the timed-out request was not accepted and requires an operational recovery path.
