# 2026 SK AI Idea 리그 제출 초안

## 제출 설정

- 활용 Tool 구분: **① 일반**
- 중심 도구: OpenAI Codex
- 결과물: Requirements Impact Refiner 0.4.0 Public Preview
- 공개 저장소: https://github.com/sdj7072/requirements-impact-refiner
- 라이선스: MIT

## 사례명

**코드를 바꾸기 전에 놓친 영향을 찾는 Requirements Impact Refiner**

대안:

1. 코드를 바꾸기 전에 영향부터 묻는 AI Agent Skill
2. 바이브 코딩의 변경 사각지대를 줄이는 저장소 기반 영향 분석
3. 요구사항 한 줄을 근거 있는 변경 계획으로 바꾸는 AI 안전장치
4. AI 개발의 빠른 구현과 안전한 변경을 잇는 Impact Refiner

## 사례 개요

AI 코딩 도구는 요청한 변경을 빠르게 구현하지만, 그 변경이 기존 권한, 저장 데이터, 모바일 클라이언트, 재시도 정책에 미치는 영향은 놓칠 수 있습니다. Requirements Impact Refiner는 구현 계획을 세우기 전에 저장소의 코드·테스트·스키마·문서를 확인해 유지해야 할 동작, 변경 영향, 근거 수준, 사용자 결정 사항, 회귀 검증 기준을 정리하는 Agent Skill입니다.

2026년 8월 Public Preview(0.4.0)를 구현하고 Codex·Claude Code용 패키지, Python 표준 라이브러리 기반 검증기, 반복 평가 체계를 공개했습니다. 통제 평가에서 결제 변경의 세 가지 위험을 저장소 사실과 엄격히 연결한 건수는 8/15에서 15/15로 늘었고, 기존 계획 흐름을 대신 시작한 위반은 3/5에서 0/5로 줄었습니다. 핵심 동작 최종 평가는 24/25(알려진 실패 1건), 워크플로 연동 평가는 30/30이었습니다. 이 수치는 특정 기록 환경에서 측정한 품질 대리 지표이며, 실제 현업의 시간·비용 절감이나 다른 모델·클라이언트·업무 환경의 성과를 뜻하지 않습니다.

## 1. 배경 및 문제 정의 (Why)

AI 코딩 도구를 사용하면 “프로필 API의 `displayName`을 `name`으로 바꿔줘”와 같은 요청을 빠르게 코드로 옮길 수 있습니다. 하지만 이 변경은 API 한 줄에 그치지 않을 수 있습니다. 기존 모바일 앱이 `displayName`만 읽고 있을 수 있고, 사용자 기기에 저장된 캐시 JSON이 같은 필드명을 사용하고 있을 수 있으며, 공개 변경 이력에는 한 버전 동안 하위 호환성을 유지한다는 약속이 있을 수 있습니다.

이 도구가 다루려는 문제는 세 가지입니다.

1. 요구사항 명확화는 주로 “무엇을 만들 것인가”에 집중하고, 저장소 근거를 따라 “어디까지 함께 영향을 받는가”를 일관되게 추적하지 않습니다.
2. AI 응답은 추정과 저장소에서 확인한 사실을 섞어 제시할 수 있어, 추가 확인이 필요한 부분을 구분하기 어렵습니다.
3. 위험을 발견해도 해결된 위험과 사용자가 감수하기로 한 위험이 구분되지 않거나, 기존 기획·계획 워크플로를 AI가 대신 시작해 역할이 겹칠 수 있습니다.

특히 바이브 코딩에서는 국소적으로 맞는 구현이 기존 권한 경계, 저장 포맷, 호환성, 결제 재시도 의미론을 조용히 깨뜨릴 수 있습니다. 구현 속도를 늦추는 대규모 사전 문서가 아니라, 계획 직전에 짧고 근거 있게 변경 영향을 점검하는 안전장치가 필요했습니다.

## 2. 구현 방법 및 활용 Tool (How / What)

OpenAI Codex를 활용해 Agent Skills 표준을 따르는 저장소 인식형 스킬을 설계·구현하고, Git 이력과 자동화된 평가 결과를 근거로 반복 개선했습니다. 핵심 흐름은 다음과 같습니다.

1. 사용자가 제안한 변경을 `REQ-###` 요구사항으로 기록합니다.
2. 관련 코드, 테스트, 스키마, 설정, 문서를 검사해 유지해야 할 현재 동작을 `INV-###`로 남깁니다.
3. 기능, 데이터, 권한, 인터페이스, 재시도, 호환성 등의 영향을 `IMP-###` 목록으로 만들고 각 항목을 `verified`, `inferred`, `unknown`으로 구분합니다.
4. 사용자 선택이 필요한 경우 2~3개의 구체적인 대안을 제시하고, 실제 선택만 `DEC-###`로 기록합니다.
5. 요구사항이 바뀌면 현재 검사 범위에서 식별된 영향 목록을 다시 계산해 해결·완화·유지·수용·보류·신규 영향을 구분합니다.
6. 구현 후 확인할 회귀 기준을 `AC-###`로 연결한 뒤 기존 계획 워크플로에 전달합니다.

같은 분석 결과에서 짧은 `Change Impact Summary`와 상세 검증 보고서를 함께 생성하도록 했습니다. 선택적으로 로컬 코드 그래프 provider를 사용해 설정한 탐색 범위 안에서 간접 영향 경로도 확인하며, 탐색하지 못한 영역은 `unknown frontier`로 남깁니다. 네트워크 연결이나 외부 도구 자동 설치 없이 동작하도록 설계했습니다.

대표 입력 예시는 다음과 같습니다.

> 계획 전에 프로필 API의 `displayName`을 `name`으로 변경할 때 API, iOS DTO, 저장된 캐시 경로에 미치는 영향을 정제해 줘. 기존 클라이언트는 한 버전 동안 호환되어야 해.

이 요청에 대해 스킬은 모바일 디코더, 저장된 JSON, 하위 호환성 약속을 서로 다른 영향으로 분리하고, 즉시 변경·두 필드 병행·명시적 마이그레이션 정책 같은 선택지를 제시합니다. 사용자가 선택하기 전에는 특정 정책을 결정된 사실처럼 요구사항에 넣지 않습니다.

Codex 플러그인, Claude Code 플러그인, 일반 Agent Skills 호환 설치 경로를 같은 기준 스킬에서 제공하고, Superpowers·Claude feature-dev·Spec Kit 등 기존 워크플로와 역할이 겹치지 않도록 진입·종료 경계를 분리했습니다.

## 3. 핵심 가치 (Value Proposition)

### 3-1. Biz. Impact

현재 단계는 2026년 8월에 제작한 Public Preview로, 실제 조직 적용에 따른 시간·비용 절감 수치는 아직 측정하지 않았습니다. 대신 같은 유형의 요청을 반복 실행하는 통제 평가를 만들고, 스킬 적용 전후의 품질 대리 지표를 저장소에 원문과 함께 보존했습니다.

| 검증 항목 | 스킬 미적용 | 스킬 적용 | 관찰된 개선 |
| --- | ---: | ---: | ---: |
| 결제 변경의 3대 위험을 저장소 근거와 엄격히 연결 | 8/15 | 15/15 | 7건 증가, 53.3% → 100% |
| 이미 승인된 영향 보고서 뒤의 계획 흐름을 스킬이 침범 | 3/5 | 0/5 | 5회 통제 평가에서 위반 3건 감소 |
| 핵심 동작 최종 평가 | 비교 구성 없음 | 24/25 | 1건의 알려진 실패 공개 |
| 워크플로 연동 최종 평가 | 초기 25/30 | 30/30 | generic 진입 경계 5건 보완 |

별도 봉인 평가에서는 85개 실행 모두 런타임 결과를 만들었고 사람 판정 400개 항목을 통과했습니다. 다만 기계 검증은 84/85였으며, 이 결과는 지원 인증이 아닙니다.

현재 확인한 효과는 시간 절감이 아니라 통제 평가에서 관찰된 개발 의사결정 품질의 변화입니다.

- 변경 전에 호환성·데이터·권한·재시도 위험을 눈에 보이는 목록으로 전환
- 코드에서 확인한 사실과 추론·미확인 영역을 분리해 검토 우선순위 명확화
- 사용자가 선택하지 않은 정책을 AI가 임의로 확정하는 위험 감소
- 회귀 기준을 구현 계획에 넘겨 이후 검토에 사용할 수 있게 함

향후 실제 조직 적용 시에는 변경당 분석·검토 시간, 계획 이후 요구사항 재수정 횟수, 구현 후 발견된 회귀 수, 영향 항목의 사전 발견률을 측정할 예정입니다.

### 3-2. 확장 가능성

Requirements Impact Refiner는 특정 사내 시스템이나 프로그래밍 언어를 전제로 설계하지 않았습니다. 저장소에서 확인 가능한 코드·테스트·스키마·설정·문서를 근거로 삼고, Agent Skills 형식과 Python 표준 라이브러리 기반 CLI를 사용합니다.

다음 조건을 갖춘 조직이라면 시범 적용을 검토할 수 있습니다.

- Git 등으로 관리되는 소프트웨어 저장소
- 저장소를 읽을 수 있는 AI 코딩 에이전트
- 구현 전에 구체화된 변경 요구사항과 검사 범위

설치 후 “계획 전에 이 API 변경의 영향을 정제해 줘”처럼 변경과 범위를 함께 제시하면 됩니다. API 필드 변경뿐 아니라 권한 정책, 데이터 삭제와 보존, 캐시 무효화, 결제 재시도, 공유 링크, 오프라인 동기화, 백그라운드 작업 등을 같은 검토 구조로 다루도록 설계했으며, 환경별 추가 검증이 필요합니다.

영어를 기준 문서로 사용하면서 한국어와 일본어 전체 번역본을 함께 제공했고, Codex·Claude Code·일반 Agent Skills 클라이언트가 하나의 기준 동작을 공유하도록 패키징했습니다. 환경별 검증 상태는 `verified`, `not verified`, `blocked`를 구분해 공개하므로, 다른 조직이 자신의 환경에서 추가 검증해야 할 범위도 파악할 수 있습니다.

### 3-3. 혁신성

일반적인 AI 요구사항 정리는 더 좋은 설명이나 더 상세한 구현 계획을 만드는 데 집중합니다. 이 사례는 그 사이에 존재하는 “저장소 근거 기반 변경 영향 정제”를 독립된 단계로 만들었다는 점이 다릅니다.

차별화 포인트는 다음과 같습니다.

1. **근거 수준 분리:** 자신 있게 말하는 정도가 아니라 실제 저장소에서 확인했는지를 기준으로 `verified`, `inferred`, `unknown`을 구분합니다.
2. **위험의 상태 관리:** 발견, 완화, 해결, 수용, 보류를 분리하고, 수용에는 반드시 사용자의 명시적 결정이 연결됩니다.
3. **영향 목록 재계산:** 하나의 결정을 반영한 뒤 그 항목만 닫지 않고 현재 검사 범위에서 식별된 영향 목록을 다시 계산해 새로 생긴 영향과 다시 열린 위험을 표시합니다.
4. **기존 AI 워크플로와 공존:** 브레인스토밍이나 구현 계획을 대신하지 않고, 요구사항이 정해진 뒤 계획을 세우기 전 단계에서 작동합니다.
5. **검증 가능한 AI 산출물:** 대화형 답변에서 끝내지 않고 계보, 해시, 안정적 식별자, 결정적 Delta를 가진 보고서와 검증기를 제공합니다.
6. **한계까지 결과에 포함:** 정적 분석이 놓칠 수 있는 영역, 실행하지 못한 환경, 알려진 확률적 실패를 숨기지 않고 다음 검토 대상으로 남깁니다.

핵심 아이디어는 구현 직전에 잠깐 멈춰 “이 변경이 현재 동작 중인 무엇에 영향을 주는가”를 저장소 근거로 확인하게 하는 것입니다.
