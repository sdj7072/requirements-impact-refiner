# Requirements Impact Refiner v0.6 Instant Report and Performance Design

**Date:** 2026-08-25

**Status:** Approved in conversation; written design awaiting final review

**Parent design:** `2026-08-25-v0.6-production-readiness-design.md`

**Impact report:** `.requirements-impact-refiner/reports/RPT-001/revision-0002.md`

## 1. Problem

The current automatic flow makes a user wait for a repository scan before it
shows useful information. Repeated requests may rebuild evidence that already
exists, the graph collector can spend most of its budget on generated files,
and the compact renderer flattens otherwise useful structure into a dense
paragraph. This wastes wall time and context tokens while making the result
harder to act on.

v0.6 changes the default interaction from “scan, then show” to
“show the last trustworthy result, then revalidate only what changed.” The
system must keep its original purpose: a request to change A must still expose
possible regressions in indirect consumers C, D, and Z. Speed is never reported
as complete coverage.

## 2. Goals and non-goals

Goals:

- show a relevant completed report within 300ms at p95;
- perform zero graph or model work for an exact requirement/source match;
- bound the default changed-source revalidation path to 3 seconds at p95;
- preserve indirect-impact seeds, invariants, and unknown frontiers;
- measure cache status, bytes, estimated tokens, and elapsed time by phase;
- restore a readable sectioned report in Korean, English, and Japanese.

Non-goals:

- no background daemon or persistent network service;
- no automatic provider installation or network access;
- no automatic detailed LLM refinement;
- no cross-repository or merely text-similar report reuse;
- no claim that estimated tokens equal a provider invoice.

## 3. Interaction model

The bootstrap uses a two-call local flow.

1. `rir_previous` performs a bounded lookup and returns one of `none`, `fresh`,
   `stale`, or `ambiguous` plus renderer-owned display text.
2. `fresh` ends the default flow immediately. No provider, graph, or LLM call
   is allowed.
3. `stale` is displayed before new work begins. The bootstrap then calls a
   delta-aware `rir_scan` with the selected immutable revision, changed paths,
   prior impact seeds, and preserved invariants.
4. `none` runs the existing bounded Fast Scan.
5. `ambiguous` does not guess. It names the candidate report IDs and asks for
   the missing discriminator.
6. Detailed controller refinement remains an explicit second-turn choice.

The protocol does not assume host-level background execution. A compatible
client can display the `rir_previous` result as an intermediate message, then
perform the bounded scan. Clients without intermediate rendering still receive
the previous-report block first in the final structured response.

## 4. Report identity and freshness

A reusable report is selected only when all identity fields agree:

- canonical repository root digest;
- normalized requirement-lineage digest;
- exact ordered repository-evidence digest, preserving duplicates;
- report ID and immutable revision digest;
- canonical compact-state digest as well as immutable Markdown digest;
- installed payload identity and schema version.

Freshness compares the stored source-inventory digest with the current bounded
inventory. A report record stores its creation timestamp, Git commit when
available, source-inventory digest, requirement and evidence digests, canonical
state digest, payload digest, and whether every inventory source was proved
Git-tracked at the clean baseline. Finalize proves the union of inventory paths
and explicit graph/Fast Scan seed paths against raw blobs from one captured
commit, recursively resolving initialized submodule gitlinks.
The lookup response adds changed-file count and an explicit `fresh` or `stale`
label. Missing Git metadata is displayed as unavailable and never prevents
content-digest validation.

Concurrent readers bind every displayed field to one immutable revision
digest. A refresh may publish a new revision only through the existing atomic
publish path; it cannot combine an old header with a new body or update the
current pointer before validation succeeds.

## 5. Delta revalidation and indirect impacts

The delta scan seeds from four sources, in priority order:

1. directly changed source files;
2. nodes and paths selected by the previous report;
3. preserved invariants and acceptance criteria;
4. request terms not already represented by the first three sources.

Generated and tool-owned directories such as `.git`, `.mypy_cache`, quality
virtual environments, graph caches, report storage, and evaluation results are
excluded before node budgeting unless the request explicitly targets them.
Repository ignore files may add exclusions but cannot remove explicit request
seeds.

The 3-second deadline is hard for the default path. If providers or the built-in
collector cannot establish a path before the deadline, the system returns the
previous report, the changed-file summary, every surviving frontier, and a
partial-coverage label. It never converts timeout, provider absence, or a
zero-path receipt into `complete`.

The regression corpus includes A-to-C/D/Z fixtures where indirect consumers
are not textually similar to the request. A change is acceptable only when the
old indirect path remains selected, is explicitly superseded by verified new
evidence, or survives as an unknown frontier.

## 6. Token and latency budgets

The controller records per-phase metrics:

- lookup elapsed milliseconds and bytes read;
- inventory/delta elapsed milliseconds and cache status;
- compact graph serialized bytes;
- previous-state bytes reused versus new evidence bytes;
- estimated model input/output tokens when a model phase occurs.

Token estimates use a documented deterministic byte-based approximation unless
the client reports actual usage. Actual and estimated values use different
fields. Reused report prose is referenced by digest and summarized once; the
same compact graph, prior state, or evidence row is never serialized twice in
one model request.

Release performance gates use pinned fixtures and compare v0.6 against the
v0.5 baseline:

- previous lookup p95 at or below 300ms;
- exact-match graph and model call counts equal zero;
- default delta path p95 at or below 3 seconds;
- no increase in unknown-frontier loss;
- lower median estimated prompt tokens on repeated and changed-source cases.

## 7. User-facing report structure

Compact output preserves complete Markdown blocks and follows this order:

1. status and risk;
2. previous-result identity and freshness;
3. numbered possible impact paths;
4. for each shown impact: cause, possible breakage, affected user or feature,
   and prevention/check;
5. evidence source and confidence;
6. unknown frontier and omitted-item count;
7. elapsed time, cache, bytes, and token metrics;
8. the single next action.

The design restores the hierarchy of the older report templates without their
wide mobile-hostile tables. Simple mode omits provenance. Balanced mode shows
selected provenance. Technical mode adds provider, confidence, locations,
receipt ID, byte counts, and omission counts.

Korean, English, and Japanese render from the same semantic field catalog.
Paths, IDs, provider names, evidence enums, lifecycle values, digests, and the
Superpowers handoff marker remain untranslated. Golden snapshots require the
same field set and warning states in every locale. The 180-word Fast Scan cap
remains, but truncation drops the lowest-priority complete block rather than
flattening or cutting a safety warning.

## 8. Compatibility and failure behavior

`rir_scan`, `rir_begin`, `rir_trace_impact`, and `rir_finalize` remain
compatible. `rir_previous` and the optional prior-revision/delta fields are
additive. CLI fallback gains a matching `previous` command. Older stored
reports without a complete v2 context remain readable as immutable artifacts
but are not selected or displayed by previous lookup. They return `none` until
a verified v2 context is published. Freshness additionally requires stable
HEAD before and after the proof, an explicitly scoped Git directory/worktree,
no tracked or untracked changes, no relevant ignored inventory source, and no
assume-unchanged or skip-worktree flags in the repository or submodules.
Finalize and lookup compare exact HEAD, status, index-flag, and recursive
submodule snapshots before and after their proof windows. A narrowly gated
interrupted v1 publication may migrate exact controller metadata and context to
v2, but its source proof remains untrusted and therefore stale until refreshed.

Unsafe paths, malformed pointers, digest mismatch, ambiguous lineage, or
non-private state fail closed without revealing report content. A missing or
unavailable graph provider is a disclosed frontier, not an installation
prompt. A token or time budget overflow returns partial structured output; it
does not discard the previous valid revision.

## 9. Acceptance criteria

- same-repository and same-lineage lookup is p95 <= 300ms;
- a repository or requirement digest mismatch never displays the prior body;
- exact source/request identity triggers zero provider, graph, and LLM calls;
- changed-source default scanning is p95 <= 3 seconds and returns the previous
  report plus frontier on timeout;
- generated directories do not consume the default source/node budget;
- A-to-C/D/Z fixtures preserve indirect impacts or disclose them as unknown;
- concurrent lookup/refresh never mixes immutable revisions;
- all per-phase cache, byte, elapsed, and token fields are deterministic;
- sectioned en/ko/ja snapshots have semantic parity and remain within budgets;
- detailed refinement occurs only after explicit confirmation;
- existing controller, CLI, MCP, canonical bytes, and report lineage tests stay
  green on Python 3.9, 3.11, and 3.13.
