# Requirements Impact Refiner v0.6 Production-Readiness Design

**Date:** 2026-08-25

**Status:** Approved design; implementation and public release remain gated

**Impact report:** `.requirements-impact-refiner/reports/RPT-001/revision-0002.md`

**Performance and report addendum:**
`2026-08-25-v0.6-instant-report-performance-design.md`

## 1. Goal

Raise Requirements Impact Refiner from a strong public preview to a release-grade
v0.6.0 without weakening its existing safety model. The work adds enforceable
static-quality gates, decomposes the controller behind a compatible facade,
validates a real optional graph provider, localizes the complete user journey,
seals current-payload client evidence, and publishes only after every release
gate passes.

The project keeps its current runtime promise: the default plugin path uses only
the Python standard library, performs no automatic network access or provider
installation, and preserves incomplete coverage as an explicit frontier.

The default user journey also follows the approved performance addendum: show
the latest same-lineage immutable report first, skip all repeated work on an
exact identity match, bound changed-source revalidation to three seconds, and
run detailed model refinement only after explicit confirmation.

## 2. Release rule

The release is fail-closed. No public `v0.6.0` tag or GitHub Release may be created
until all of the following are green on the exact candidate payload:

1. unit, integration, packaging, lineage, graph, and renderer tests;
2. compile checks on Python 3.9, 3.11, and 3.13;
3. Ruff lint and format checks;
4. Mypy checks for every shipped module and the evaluation harness;
5. branch-aware coverage with a repository total of at least 80 percent;
6. Bandit static security checks with no unresolved medium-or-higher finding;
7. the pinned ast-grep canary and real-corpus graph score;
8. Codex and Claude release matrices, five first-attempt repetitions per case;
9. secret scan, evidence manifest, scoring, and adjudication verification;
10. local candidate-tag canaries whose payload digest matches the release candidate.

Authentication, cost, rate-limit, provider, secret, or evidence-integrity
failure is a release blocker, not a skipped pass.

## 3. Delivery sequence

The work is split into four independently reviewable subprojects. Each produces
a green main branch before the next begins.

### 3.1 Quality foundation

Add a `pyproject.toml` that contains development-only Ruff, Mypy, coverage, and
Bandit configuration. CI installs pinned development-tool versions; plugin
manifests and runtime scripts remain free of third-party imports.

The quality workflow runs deterministic local commands identical to CI. A
single command entry point documents and executes the complete local gate so a
release cannot rely on undocumented CI-only behavior.

### 3.2 Controller and graph architecture

`scripts/rir_controller.py` remains the compatibility facade. Existing public
classes, functions, exceptions, CLI behavior, MCP behavior, canonical bytes,
and file locations remain import-compatible.

Internal responsibilities move into focused modules:

| Module | Responsibility |
| --- | --- |
| `rir_contracts.py` | request dataclasses, enums, bounded input validation |
| `rir_storage.py` | safe path traversal, private files, locks, CAS, recovery |
| `rir_graph_delivery.py` | trace intent, receipt validation, compact delivery |
| `rir_lineage.py` | key allocation, revision rules, Delta, carry-forward state |
| `rir_finalize.py` | analysis validation, state construction, publish orchestration |
| `rir_controller.py` | stable imports and orchestration facade only |

The canonical and installed-skill copies stay byte-identical. Characterization
tests capture the facade before each extraction and compare return values,
exceptions, canonical JSON/Markdown bytes, filesystem modes, and transaction
recovery behavior afterward.

Python AST and JS/TS structural signals remain built in. Multi-language proof
comes first from a pinned, read-only ast-grep canary rather than a new mandatory
runtime dependency. The canary verifies executable digest, version, invocation
shape, output schema, source provenance, and missing/unsupported behavior.

A licensed public corpus is pinned by repository and commit SHA. Corpus
selection requires MIT, BSD, or Apache-2.0 compatibility and preserved license
text. Its expected relationships are independently curated; graph precision,
recall, unknown frontier, runtime, and output-size metrics are stored as literal
release evidence rather than inferred from the implementation.

## 4. User-facing presentation

Locale resolution supports explicit `en`, `ko`, and `ja`. An explicit request
or repository setting wins; character-based inference is the fallback; English
is the final fallback. Locale affects presentation only and never scan identity,
graph evidence, state identifiers, or canonical lifecycle semantics.

Fast Scan output preserves Markdown line structure. It no longer flattens every
block into one paragraph. Balanced Korean output follows this shape:

```text
## 빠른 영향도 검사

**위험도:** 치명적

### 발생 가능한 영향 경로

1. `.codex-plugin/plugin.json` → `.github/workflows/ci.yml`
   - 위험: 권한·개인정보, 인터페이스, 회귀
   - 근거: builtin · structural-inferred
   - 위치: `.codex-plugin/plugin.json`, `.github/workflows/ci.yml`

### 미확인 범위

- ast-grep, codegraph, scip을 사용할 수 없어 내장 분석을 사용함
- 내장 분석의 자원 한도에 도달함

### 검사 정보

- 범위: 부분
- 시간: 2240ms
- 캐시: 미적중

상세 영향도 정제를 진행할까요?
```

Simple mode omits provenance rows. Technical mode includes provider,
confidence, locations, receipt coverage, and omission counts. The renderer
budgets complete blocks, never cuts a path or safety warning mid-row, preserves
newlines, and remains at or below 180 words in every locale.

Detailed impact reports use the same locale catalog for headings, statuses,
questions, validation summaries, and handoff guidance. Machine identifiers,
file paths, provider names, evidence enums, lifecycle states, and the exact
Superpowers handoff marker remain untranslated.

## 5. Evaluation evidence

The release catalog covers positive, negative, integration, and two-turn
confirmation behavior. Codex and Claude run in isolated repositories and
sessions with the exact release-candidate payload and the user's selected model.

Each selected case runs five times without selective retry. The release gate
requires every selected first attempt to pass runtime, controller-call,
mechanical, graph, presentation, and evidence-integrity checks. A retry may be
recorded for diagnosis but cannot replace a failed release-gate observation.

Each run records client version, model, reasoning level when reported, plugin
version, payload digest, tool-call order, receipt digest, final bytes, stderr,
duration, and token usage when the client reports it. Raw evidence is scanned
before entering the repository. Suspicious artifacts are moved to quarantine
outside the repository; the batch remains blocked.

The final evidence directory contains raw transcripts, selected finals,
controller observations, scores, adjudications, environment probes, payload
inventory, canonical manifest, and a human-readable report. Every derived
claim points back to sealed bytes.

## 6. Versioning and distribution

Version `0.6.0` is updated atomically across Codex and Claude manifests, skill
metadata, marketplace metadata, documentation, packaging tests, and expected
release evidence. Installation documentation uses the immutable v0.6.0 tag for
release instructions and keeps `main` only for explicit development installs.

After all code, evidence, and local candidate gates pass:

1. merge the release candidate to `main`;
2. verify remote CI on the exact commit;
3. create the annotated `requirements-impact-refiner--v0.6.0` tag locally;
4. install from the local tag in fresh Codex and Claude environments;
5. compare installed payload digests with the release inventory;
6. push the immutable tag only after both local tag canaries pass;
7. verify one remote tag-install canary without changing the tag;
8. create a GitHub Release with generated and reviewed notes;
9. publish the canary result and compatibility table;
10. update GitHub description and topics;
11. prepare and submit marketplace metadata where submission is available.

Marketplace acceptance is external and cannot be reported as complete until
the marketplace confirms it.

## 7. Failure handling and rollback

- A quality or deterministic-test failure stops the current subproject.
- A controller parity failure restores the last green extraction boundary; it
  does not trigger additional simultaneous refactoring.
- Provider or corpus disagreement remains an unknown frontier and blocks the
  support claim for that provider.
- Live-client authentication or rate-limit failure records `blocked` and stops
  the release matrix.
- A secret finding quarantines the artifact and blocks public evidence.
- A local tag-install digest mismatch prevents the tag from being pushed.
- A remote tag-install digest mismatch blocks the GitHub Release and is never
  repaired by replacing the public tag.
- No force push, tag replacement, selective evidence deletion, or failed-run
  substitution is allowed.

## 8. Acceptance criteria

The program is complete only when:

- all current tests and new quality gates pass locally and in CI;
- controller facade parity is mechanically demonstrated after decomposition;
- Fast Scan and detailed reports are readable and equivalent in en/ko/ja;
- the ast-grep canary and pinned public corpus meet their literal score gates;
- Codex and Claude five-repetition matrices have no first-attempt failure;
- all evidence is sealed, secret-clean, and reproducible;
- every version and digest agrees with the immutable tag;
- local tag-install canaries pass before the tag is pushed, and the remote
  tag-install canary passes before the GitHub Release is created;
- the GitHub Release exists and documentation names only verified support;
- marketplace submission state is reported exactly as submitted, accepted,
  rejected, or blocked.

Until every release criterion passes, the repository may improve and merge
internally, but the public status remains pre-release and no public v0.6.0 tag
is created.
